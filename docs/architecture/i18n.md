# i18n architecture

This document covers the **localisation system**: copy module shape, the
reactive `useCopy()` hook, the `Copy` type's widening pattern, and what's
deferred for production.

Currently the app ships three locales: **English (en)**, **isiZulu (zu)**,
**Afrikaans (af)**. South Africa has 11 official languages — these three
are the demo's most-spoken set. The architecture is structured so adding
the remaining eight is a drop-in.

---

## The copy module

All user-facing strings live in **one central module per locale**:

```
apps/stokvel-app/src/copy/
├── en.ts          ← canonical, defines the shape
├── zu.ts          ← isiZulu translation
├── af.ts          ← Afrikaans translation
├── types.ts       ← Copy type, Locale type, LOCALES list
├── locale-store.ts ← reactive store + localStorage persistence
└── index.ts       ← public API (useCopy, getCopy, interpolate, plural)
```

Components import only from `index.ts`. They never reference `en.ts`
directly — that would defeat reactivity.

### Shape

A nested object grouped by feature:

```ts
copy.dashboard.balanceTitle    // 'Total balance'
copy.contributions.statusConfirmed  // 'Confirmed'
copy.errors.unexpected         // 'Something went wrong. Please try again.'
copy.pinLock.welcome           // 'Welcome back, {name}'
```

Strict TS — misspelt keys fail the build. The shape is **defined** by
`en.ts` (every locale must satisfy it).

## Why a hook, not Context

We considered two reactive approaches:

### Option A: React Context (the obvious one)

```ts
const CopyContext = createContext<Copy>(en);
function useCopy() { return useContext(CopyContext); }

<CopyContext.Provider value={zu}>
  <App />
</CopyContext.Provider>
```

**Why we rejected it.** Every consumer needs to be inside the provider.
For a small app this is fine, but for a tree with many independent
features (mutation handlers, error boundaries, top-level error UI), it
gets fragile. Also, every locale change re-renders the whole tree — fine
in practice, but Context makes that re-render path implicit.

### Option B: External store + `useSyncExternalStore` (what we did)

```ts
// locale-store.ts
let currentLocale: Locale = readStoredLocale();
const listeners = new Set<() => void>();

export const localeStore = {
  getLocale: () => currentLocale,
  getCopy: () => COPY_BY_LOCALE[currentLocale],
  subscribe: (cb) => { listeners.add(cb); return () => listeners.delete(cb); },
  setLocale: (next) => {
    if (next === currentLocale) return;
    currentLocale = next;
    localStorage.setItem(LOCALE_STORAGE_KEY, next);
    for (const cb of listeners) cb();
  },
};

// index.ts
export function useCopy(): Copy {
  return useSyncExternalStore(localeStore.subscribe, localeStore.getCopy, localeStore.getCopy);
}
```

**What this gives us:**

- **No provider required.** Any component, any depth, any time can call
  `useCopy()`. No "did I forget to wrap that error boundary in a
  provider?" debugging.
- **Snapshot accessor for non-React contexts.** Some places are not
  React components — error formatters in `use-login.ts`, the
  `RootErrorComponent` in `__root.tsx`. They call `getCopy()` (a plain
  function returning the current copy snapshot) instead of the hook.
- **Drop-in compatible with `react-i18next`** later. The per-feature
  key shape (`copy.dashboard.balanceTitle`) and the hook-based API
  match `react-i18next`'s conventions. If we ever need pluralisation
  rules, gender, ICU MessageFormat, locale-aware date/number formats,
  swapping in `react-i18next` is mechanical.

### When to use which

| You're in… | Use |
|---|---|
| A function component that renders text | `const copy = useCopy()` |
| A custom hook that builds strings reactively | `const copy = useCopy()` |
| A non-component callback (event handler, error formatter) | `const copy = getCopy()` |
| A module-level constant (e.g. `STATUS_LABEL` map) | **Don't** — move it inside the component or call `getCopy()` lazily |

Module-level constants computed from `copy` are a footgun: they capture
the locale at module load (English) and never react to changes. The
prior status-label maps in feature views were an example — refactored
into an inline `getStatusLabel(copy, status)` helper that takes the
current copy as an argument.

## Locale switching

The picker is a small dropdown next to the Online indicator in the
AppWindow header. Implementation in `layout/LanguageSwitcher.tsx`:

```ts
const locale = useSyncExternalStore(
  localeStore.subscribe,
  localeStore.getLocale,
  localeStore.getLocale,
);

<DropdownMenuRadioGroup
  value={locale}
  onValueChange={(v) => localeStore.setLocale(v as Locale)}
>
  {LOCALES.map((l) => (
    <DropdownMenuRadioItem key={l.code} value={l.code}>
      {l.nativeLabel}
    </DropdownMenuRadioItem>
  ))}
</DropdownMenuRadioGroup>
```

Picking a locale:

1. Writes to the store via `setLocale(next)`.
2. Store updates `currentLocale` and persists to
   `localStorage` under `seyva-locale`.
3. Notifies all subscribers; every component using `useCopy()` rerenders
   with the new tree.

Persistence: a returning user sees their last picked language. Not
sensitive — non-encrypted localStorage is fine. Survives sign-out
(deliberately — language preference isn't user-state, it's
device-preference).

## The `Copy` type widening pattern

`en.ts` is the canonical shape:

```ts
export const copy = {
  app: { name: 'Seyva Stokvel', tagline: 'Savings built on trust.' },
  // ... rest
} as const;
```

The `as const` makes every leaf string a **literal type**:

```
typeof copy.app.name  // 'Seyva Stokvel' (literal)
typeof copy.app.tagline  // 'Savings built on trust.' (literal)
```

When `zu.ts` declares its translation:

```ts
export const copy: Copy = {
  app: { name: 'Seyva Stokvel', tagline: 'Imali eyakhelwe phezu kwethemba.' },
  ...
}
```

…TypeScript would error: *"Type 'Imali eyakhelwe phezu kwethemba.' is
not assignable to type 'Savings built on trust.'"* The literal types
from `en.ts` are too strict.

The fix is in `types.ts`:

```ts
import type { copy } from './en.js';

/** Widen literal string types to `string` so other locale files satisfy the shape. */
type Widen<T> = T extends string
  ? string
  : T extends readonly (infer U)[]
    ? readonly Widen<U>[]
    : T extends Record<string, unknown>
      ? { [K in keyof T]: Widen<T[K]> }
      : T;

export type Copy = Widen<typeof copy>;
```

`Widen<T>` recursively walks the type tree, replacing every literal
string with `string`. Other locale files implement `Copy` and
TypeScript is happy.

This means **the EN shape is enforced** (you can't add a key to `zu.ts`
that doesn't exist in `en.ts`) but **the literal values aren't**.

## Placeholder interpolation + pluralisation

```ts
import { interpolate, plural } from '../copy/index.js';

interpolate('Hello, {name}', { name: 'Nomsa' });
// → 'Hello, Nomsa'

plural({ one: '{count} member', other: '{count} members' }, 3);
// → '3 members'
```

Both are tiny utilities (~10 lines each) defined in `copy/index.ts`.
Not as expressive as ICU MessageFormat (no gender, no select, no nested
plurals), but enough for the demo's strings.

`react-i18next` would slot in here too — its `t()` function does
interpolation with the same `{key}` syntax.

## What's deferred

### `Intl` formatters per-locale

Currently `@seyva/utils` has SA-locale-hardcoded formatters:

```ts
formatMoney(50000)     // 'R 500,00'  (always en-ZA)
formatPhone('+27821000001')  // '+27 82 100 0001'  (always en-ZA)
formatDate('2025-01-01')     // '1 Jan 2025'  (always en-ZA)
```

Production would parameterise these by locale:

```ts
formatMoney(50000, 'zu')  // → 'R 500,00' or 'R500,00' depending on isiZulu convention
```

The `Intl.NumberFormat` and `Intl.DateTimeFormat` browser APIs handle
this. The seam exists (formatters are in a single package), but the
per-locale variants aren't wired.

### Right-to-left support

If we ever expand to Arabic markets (or test markets that need RTL),
we'd add:

- `dir="rtl"` on `<html>` driven by locale
- Tailwind logical properties (`ms-`, `me-` instead of `ml-`, `mr-`) —
  shadcn already uses these for some primitives, others would need a sweep
- Mirror-aware icons (chevrons, arrows)

Not started. The current locales are all LTR.

### Remaining 8 official SA languages

isiXhosa, Sesotho, Setswana, Sepedi, Xitsonga, siSwati, Tshivenda,
isiNdebele. Adding each is mechanical:

1. New `copy/<code>.ts` with the same shape as `en.ts`.
2. Add to `Locale` union and `LOCALES` list in `types.ts`.
3. Translate every key.

The third step is real work (and ideally professional translation, not
machine-translated). The architecture supports it.

### Translation management

Currently translation files are committed source code. At scale a
team would use:

- Lokalise / Crowdin / Phrase for managing translations
- A CI step that pulls latest translations into the repo
- A "translation completeness" check (every key present in every
  locale)

For three locales and ~70 keys, source-controlled is fine.

### Pluralisation rules per language

`plural({one, other}, count)` only handles the English pattern.
Languages with more plural categories (Russian: one / few / many,
Arabic: zero / one / two / few / many / other) would need a rule
table. CLDR plural rules are the standard; `Intl.PluralRules` exposes
them in browsers. Not a problem yet — none of our three locales need
more than `one/other`.

---

## Summary

The system is a **deliberately minimal** reactive locale layer that
keeps every user-facing string out of components. It's drop-in
compatible with `react-i18next` for the day a fuller solution is
needed. For three locales × 70 keys, the hand-rolled approach is
the right size.
